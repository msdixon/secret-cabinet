# STATUS.md

Dated, one-line-per-entry log of what shipped or changed. Newest first.

**Entries arrive as fragments, not direct edits.** When something ships, a decision gets made, or a notable bug gets found/fixed, add a fragment file to [`docs/status/fragments/`](docs/status/fragments/) instead of editing this file directly — see that directory's README for the filename convention and content format. This is the same pattern Towncrier (Python) and Changesets (JS monorepos) use: parallel PR branches all editing the same insertion point in one file were producing avoidable merge conflicts on every overlap, not real logical conflicts, just git seeing concurrent edits to the same spot. `node scripts/assemble-status.js` (run manually, or weekly as a step in the `secret-cabinet-project-doc-checkin` scheduled task) turns pending fragments into dated entries here and deletes the fragments it consumed — see that script's header for details.

**Entries are 1-3 sentences plus the PR/issue link — not a restatement of the PR body.** The PR carries the reasoning, the alternatives considered, and the verification steps; that's what it's for, and it stays attached to the diff permanently. This file is read into context at the start of most sessions, so its size has an ongoing cost beyond scrolling — see [#275](https://github.com/msdixon/secret-cabinet/issues/275), filed after entries drifted to ~4x their prior length in a matter of weeks.

**When this file crosses ~60KB, roll the oldest entries into `docs/status/ARCHIVE-<range>.md`** and leave a pointer here, same as the archives below. Size-triggered, not calendar-triggered — a fixed schedule doesn't track what actually made the file big.

For the *why* behind any entry, check the linked PR/issue first; deeper narrative context (what was tried, what was rejected, collaboration notes) lives in Claude's memory, not here. For current direction and open decisions, see [PROJECT.md](PROJECT.md).
