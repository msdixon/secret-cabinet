# Portrait Style Guide

Source of truth for generating member portraits (#116, #27). Every generation run — the initial batch and any member added afterward — should be checked against this file first. If a run has to deviate to get a usable result, record it in the Changelog below so the next run doesn't silently drift further.

## Status

AI-generated, proof-of-concept register for this stage of the project. Not commissioned or licensed illustration. See [MANIFEST.md](../../docs/MANIFEST.md) for the standing disclosure note.

## Baseline register (from #27)

- **Tone:** warm, etching-adjacent — not photorealistic, not cartoon/flat-vector.
- **Palette:** limited, warm-toned (sepia/candlelit register), consistent across the set — no member should read as lit or colored differently from the rest of the roster.
- **Composition:** head-and-shoulders, period-appropriate dress, plain/dark background (no scene elements — scene context is the 3D salon's job, not the portrait's, per #26/#28).
- **Line quality:** visible linework/texture (etching, engraving, ink-wash adjacent) rather than smooth airbrushed rendering.
- **Border/frame:** match whatever the member's own baseline established — a plain white/cream border, or fully borderless (image runs edge-to-edge) — consistently across the baseline and all three reactions. This guide doesn't mandate one or the other roster-wide; the existing set is split roughly evenly between bordered and borderless members. The requirement is internal consistency per member, not a specific choice (added after [#531](https://github.com/msdixon/secret-cabinet/issues/531) found several members' reaction sets silently drifting border treatment against their own baseline).
- **Camera distance/crop:** same head-and-shoulders framing and zoom level as the member's baseline across all three reactions — a reaction should never crop tighter/looser, or introduce a pose/hand gesture the baseline doesn't have (added after [#531](https://github.com/msdixon/secret-cabinet/issues/531), same finding as above).

## Known-vs-unknown likeness

- **Photographed figures** (e.g. Crowley, Yeats): generations should aim for recognizable likeness where reference material exists.
- **Pre-photographic or iconography-bound figures** (e.g. Llull, Teresa of Ávila, Ibn Arabi): there is no photographic ground truth — treat these as period-appropriate character studies consistent with the set's register, not likeness reproductions. For figures with an existing devotional/iconographic tradition, favor a secular character-study framing over reproducing religious iconography.

## Downstream use and format

**Decided 2026-07-31** (see [#26](https://github.com/msdixon/secret-cabinet/issues/26)): the existing batch-1 crop (`public/portraits/<id>.png`, portrait-oriented rectangle) is used as-is for the 3D avatar's Phase 2 billboard cards — no new crop or generation needed. Billboards (camera-facing textured planes) are the deliberate MVP, not a placeholder for something else already planned; a more sculptural avatar representation is the intended eventual direction, and full 3D character models are explicitly a long-horizon idea, not a near-term target — so don't assume billboards need re-doing once the "next" avatar phase starts. If a genuinely different rendering approach (true 3D geometry) is ever taken up, that would need its own crop/format decision at that time.

## Process

1. Batch 1: generate the full current roster (see `prompts/members/roster.json`) in one run to establish the baseline and catch consistency problems before they're spread across separate sessions.
2. Human-validate batch 1 against this guide before treating the style as locked.
3. Reconvene to confirm the baseline (or amend this guide) before generating any member added after batch 1.
4. For each member added to the roster afterward, generate one portrait against this guide, at the same time the member is added. **As of [#259](https://github.com/msdixon/secret-cabinet/issues/259)/[#435](https://github.com/msdixon/secret-cabinet/issues/435):** prompt-drafting *and* candidate generation are both automated — the in-app "Add Member" flow (`POST /api/members`, `src/routes/member.js`) drafts a style-guide-compliant prompt against this file at member-creation time, appends it to [PENDING-PROMPTS.md](PENDING-PROMPTS.md), and (when `GEMINI_API_KEY` is set) calls the Gemini API directly (`gemini-2.5-flash-image`, via `src/portrait-generation.js`) to generate a real candidate image at `public/portraits/candidates/<id>.png`. **As of [#450](https://github.com/msdixon/secret-cabinet/issues/450):** the same call also drafts the #449-decided reaction set (happy/thinking/angry) from that baseline candidate as a reference image, landing at `public/portraits/candidates/<id>-<reaction>.png`. It deliberately stops there: human validation is still the load-bearing step this guide has always required, so no candidate — baseline or reaction — touches its canonical path on its own. Run `node scripts/promote-portrait.js <id>` (and `<id>-<reaction>` for each reaction) after looking at the candidates and deciding they're good — it resizes to 512px on the long edge, places it, deletes the candidate (and, for the baseline, its `PENDING-PROMPTS.md` entry), and reminds you to add the Changelog line below yourself (that still needs an actual look at the image, same as every prior batch — the script won't write it for you).
